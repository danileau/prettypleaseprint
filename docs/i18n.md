# Translation

The languages are the files. Whatever sits in `messages/` is what the app
offers — `en.json`, the source, and `fr.json` so far — and the picker on `/me`
lists exactly those. There is no list of languages, or of their names, in the
code: adding German is adding `messages/de.json` and passing
`npm run check:messages` ([below](#adding-a-language)).

The sign-in page, the header, mail and the language picker read their words
from the catalogues through [next-intl](https://next-intl.dev); the other
screens are still English in the code, and move onto the catalogue one group of
pages at a time (#103).

## How it works

- **No locale in the URL.** There are no `/en/…` routes and no next-intl
  middleware. Every link, every redirect and every `next=` parameter is exactly
  what it was, and so is every bookmark. A language prefix would have meant
  rewriting every one of them, and every test that asserts on a redirect, for a
  choice the request can carry by itself.
- **Who sees which language**, decided per request in
  [src/i18n/request.ts](../src/i18n/request.ts) by `resolveLocale` in
  [src/i18n/locales.ts](../src/i18n/locales.ts), whose comment gives the
  reasoning:
  1. the person's own choice on `/me` (`User.preferredLocale`);
  2. the browser's `Accept-Language`, by quality, `fr-CA` falling back to `fr`
     when there is no `fr-CA.json`;
  3. the instance default: the owner's choice on `/admin/settings`, unless
     `DEFAULT_LOCALE` is set in the environment, which wins and locks the field
     ([deployment](deployment.md#language); `instanceLocale` in
     [src/lib/settings.ts](../src/lib/settings.ts));
  4. English.

  Each counts only if it names a file the build has. A stored choice for a
  language since removed — on a profile or on the settings page — is passed
  over for the next rule, and a `DEFAULT_LOCALE` naming no file is ignored;
  either is said once in the log rather than stopping the app.
- **Finding the files.** The production server is Next's `standalone` bundle
  and the image has no `messages/` directory, so the languages are whatever
  webpack found there at build time: `import.meta.webpackContext` over
  `messages/` gives both the list and a loader for each
  ([src/i18n/catalogue.ts](../src/i18n/catalogue.ts) says why that and not
  something else). Under `tsx` — the suites and scripts, which have no bundler
  — the same module reads the directory from disk. `full-test.sh`'s
  `messages-bundled` step holds the built image's map to the checkout.
- **A file's name is its code**, a BCP 47 tag written the way `Intl` writes it
  (`fr`, `pt-BR`): what `<html lang>` says, what `preferredLocale` stores, and
  what the picker shows by its name in that language (`Intl.DisplayNames`, so
  no list of names either). `check:messages` refuses a name that is not one.
- **`User.preferredLocale`** is a nullable text column, written by the picker on
  `/me` and read by every request and every email. Plain text rather than an
  enum, so that adding or dropping a language is not a migration.
- **`messages/en.json` is the source of truth.** Every key is a type
  ([src/i18n/app-config.d.ts](../src/i18n/app-config.d.ts)), so asking for a key
  English does not have — a typo, or one removed while a component still uses
  it — fails `npm run typecheck`. Every other catalogue is laid over English key
  by key (`overlay` in catalogue.ts): a key a translation lacks shows in
  English, never as its own name.
- **`<html lang>` and next-intl's formatting follow the same choice.** The root
  layout reads `getLocale()`, plurals, dates and numbers formatted through
  next-intl use the request's locale, and so do the relative times ("3 hours
  ago") in the header's Activity menu
  ([below](#what-stays-english-on-purpose)).

### What the browser is sent

Server components read the whole catalogue. Client components get only the
groups listed for their screen in
[src/i18n/client-groups.ts](../src/i18n/client-groups.ts): `AppHeader` wraps
its menus and the passkey nudge in a `NextIntlClientProvider` holding
`CLIENT_GROUPS.header`, and the sign-in page wraps its form in one holding
`CLIENT_GROUPS.signin`. The single sign-on button and the "or" between two ways
in are the `waysIn` group, sent by every screen that shows them: the sign-in
page, and the invitation and "is that still you?" screens, where only what
single sign-on added reads the catalogue so far. There is no provider in the
root layout. The language picker on `/me` is a server-rendered form and sends
nothing.

The reason is not size. Messages sent to client components travel in the
page's RSC payload, readable in its source. Sent from the root layout, every
page — the sign-in page included, to someone not signed in — would carry every
word in the app, the owner's navigation among them, and `verify:auth` asserts
that an owner-only label is *absent* from a client's page. For the same reason,
words only the owner sees are never in a client group: the server picks them
(`header.feedTitle`, `header.role`) and passes them down as props (`title`,
`roleLabel`). `verify:auth` checks the same absence in every language that
ships, with that language's words.

Both providers set `timeZone="UTC"`, so the server's own time zone is not
written into the page; nothing on the client formats a date through next-intl.

A client component asking for a group its screen does not send would render
key names, and the typecheck cannot see that — the types know every key, not
which ones were sent. `check:messages` reads every `useTranslations("…")` in a
`"use client"` file and fails when its group is not listed.

### Why next-intl, and what it costs

It is the App Router's de-facto library: server components, server actions and
client components all read the same catalogue, ICU plurals come with it, and it
works without locale routing — which is the one thing this app needed it not to
impose. Writing the equivalent here would mean owning a message formatter.

- **Licence:** MIT. What it pulls in is MIT, Apache-2.0 (`@swc/*`) and
  BSD-3-Clause (`intl-messageformat`) — all compatible with AGPL-3.0.
- **Pinned exactly at 4.14.9**, the newest release when it was added. Not an
  older, leaner 4.x: every release before 4.9.2 is covered by a published
  advisory — an open redirect in the middleware before 4.9.1
  ([GHSA-8f24-v5vv-gm5j](https://github.com/advisories/GHSA-8f24-v5vv-gm5j)),
  and prototype pollution through the experimental precompile option up to
  4.9.1 ([GHSA-4c35-wcg5-mm9h](https://github.com/advisories/GHSA-4c35-wcg5-mm9h)).
  Neither is reachable here — this app uses neither — but both would be
  reported by every scan for as long as the pin stood.
- **The weight is build-time.** Since 4.5, next-intl depends on `@swc/core` and
  `@parcel/watcher` for a message extractor this app does not use; with their
  platform binaries that is most of the lockfile entries it adds, and both run
  an install script during `npm ci`. None of it reaches the runtime image: the
  standalone bundle the runner copies traces no `@swc/core` and no
  `@parcel/watcher`, and next-intl itself is compiled into the server chunks.
- **The lockfile is npm 10's**, the npm in `node:22` that CI and the Dockerfile
  run: it keeps the nested `node_modules/next-intl/node_modules/@swc/helpers`
  entry npm 10 requires and npm 11 drops, with the `libc` fields npm 11 writes
  added back. `npm ci` passes with both. If an install with npm 11 removes the
  nested entry, CI's `npm ci` fails with "Missing: @swc/helpers@… from lock
  file": put it back, or run the install with npm 10.

### What stays English, on purpose

The JSON API, the OpenAPI document and the console at `/docs`; audit verbs
(`story.created`, …) and every log line; the PrusaSlicer helper.
These are read by programs, by the operator, or by whoever debugs a problem —
and one language there is what makes an error message searchable.

Three more are still English, and are known gaps rather than decisions:

- **Notification text in the Activity panel.** Every notification is raised as
  a key under `notification` and its values (`notify` in
  [src/lib/authz.ts](../src/lib/authz.ts)), and its email is written from
  those. The panel, though, still stores the English sentence when the
  notification is created; translating it there means storing the key and its
  values beside the text (additive columns) and building the sentence when it
  is read, with existing rows keeping their text.
- **Relative times on the screens not yet moved** ("3 hours ago", `relativeTime`
  in [src/lib/catalog.ts](../src/lib/catalog.ts)). The header's Activity menu
  passes it the request's language (`relativeTimeVoice()` in
  [src/i18n/server.ts](../src/i18n/server.ts)): `Intl.RelativeTimeFormat` in
  that language, and `time.justNow` from the catalogue for the first 45
  seconds. Every other page calls it without — `/me`'s list of orders too —
  and its dates stay English with the rest of its words until it moves; a page
  that moves passes the voice too.
- **Messages from Better Auth** (a refused passkey, for one). They come from the
  library, not from a catalogue this app owns.

### E-mail is written in the recipient's language

An email has no request to take a language from, only a person it is for, so
it is written in theirs: `User.preferredLocale`, when it is a language the app
offers, from its catalogue laid over English key by key (`catalogueFor` in
[src/i18n/catalogue.ts](../src/i18n/catalogue.ts)). Not the
language of whoever caused it — the owner moving a ticket does not decide what
language its requester is told in.

- **Notifications** go in the recipient's; **a password reset** in its
  member's; **the test message** in the owner's own.
- **An invitation** is for somebody with no account and so no choice yet, and
  mail has no browser to ask: it goes in the instance default (`DEFAULT_LOCALE`,
  else the settings page), else English. So does mail to anybody who has not
  chosen.
- **The same files.** Mail uses a `preferredLocale` only if it names a file the
  build has — the list the pages and the picker use (`offeredLocales`);
  anything else (`../en`, `EN`, a language since removed) is the instance
  default, then English, and never becomes a file name.
- **Never key names.** A key the catalogue lacks is English, and so is a
  translated message that fails to format: `translatorFor` formats the English
  message for that key with the same values. `check:messages` holds each
  translation to English's `{arguments}` and its `<tags>` — `<link>` in a
  notification email is the address to switch them off.
- **What is tested, and what is not.** `verify:queue` drives `notify` in a
  child process (`scripts/mail-locale-probe.ts`) with a throwaway catalogue it
  writes as `messages/vo.json`: not a language before the file exists, one
  after; a recipient who chose it is written to in it, with English for its
  missing and broken keys, while the owner gets English from the same event.
  That is `tsx` reading the directory at run time, not the built app, whose
  server finds catalogues in the map the bundler made at build time;
  `full-test.sh`'s `messages-bundled` step checks that the built image's map
  names every file in `messages/`, and `verify:auth` has the built app serve
  each of them. No suite sends mail from the image in a language other than
  English.
- **The owner's Mail page** previews in the instance default; `?locale=<code>`
  on it (or on a preview) writes the previews in that language, if there is a
  file for it.
- The words are under `mail.*`, with `<strong>`, `<mono>` and `<link>` tags the
  templates fill in. Every value is escaped before it reaches a message, since
  filling a message in does not escape.

## Adding a key

1. Add it to `messages/en.json`, under the group for its screen
   (`signin.form.…`, `header.nav.…`). Name it for what it *is*, not for its
   English words — `header.nav.books`, not `header.nav.theBooks`.
2. Use it: `const t = await getTranslations("signin")` in a server component,
   `const t = useTranslations("signin.form")` in a client one, then `t("key")`.
   Arguments are ICU: `"{count, plural, one {# passkey} other {# passkeys}}"`
   with `t("passkeys", { count })`.
3. In a client component, make sure its group is listed for its screen in
   `CLIENT_GROUPS` — unless only the owner sees the words, in which case the
   server reads them and passes them as a prop.
4. `npm run typecheck && npm run check:messages`.

## What `check:messages` reports

[scripts/check-messages.ts](../scripts/check-messages.ts) holds every file in
`messages/` other than `en.json` against `en.json`, and checks the client
groups. It runs in CI's `guard` job and in `scripts/full-test.sh`. Its first
line lists each translation with the name the picker gives it:
`1 translation(s): fr (Français)`.

**Warnings** are listed and the check still passes. Each is what an
English-only change leaves behind in a translation, and each costs its reader
nothing but some English. A maintainer who does not write the language must be
able to merge; the translation catches up after. So **if you do not write a
language, leave its file alone** — do not paste the English in to silence a
warning, which hides the key from the one check that would have found it.
Under GitHub Actions each warning is a `::warning` annotation on the pull
request, and `full-test.sh` adds a `WARN check-messages` line to its summary.

| warning | means | do |
|---|---|---|
| **missing** | in English, not in the translation | translate it (it shows in English until then) |
| **stale** | in the translation, gone from English | delete it |
| **shape** | a string against a group, or the reverse | match English's new structure |

**Errors** fail the check. These are broken, not merely behind:

| error | means | do |
|---|---|---|
| **empty** | `""` | translate it, or remove the key |
| **arguments** | `{name}`, `{count}`… differ from English | keep every placeholder, renamed nowhere |
| **tags** | `<link>`, `<strong>`… differ from English | keep every tag, around the words it belongs to |
| **quote** | an ASCII `'` right before `{`, `}` or `#` | use the typographic `’` |
| **malformed** | not JSON, a key containing `.`, a value neither string nor group | fix the file |
| **format** | next-intl cannot format the message — an unclosed brace, a `plural` with no `other`, a tag never closed | fix the ICU syntax; the app shows English for that key meanwhile, never the key |
| **name** | the file name is not a BCP 47 tag, is not spelt as `Intl` writes it (`pt-br` for `pt-BR`), is a code for no language (`und`, `mul`, `zxx`, `mis`), or is one `Intl.DisplayNames` cannot name (`notes`) | rename the file; the app leaves such a file out, with a warning in its log — the same rule (`languageProblem`) |
| **client components** | a `useTranslations("x")` in a `"use client"` file whose group no screen sends | add the group to `CLIENT_GROUPS` |

**quote** is ICU's quoting rule: an ASCII apostrophe before a brace starts a
quoted literal, so `l'{x}` renders as "l{x}" with no error anywhere. The
catalogue uses `’` throughout, which ICU leaves alone.

The check sees keys, not meanings: when you change what an English string
says, change or remove its translations too.

## Moving a screen onto the catalogue

- Server component: `getTranslations("group")`. Client components:
  `useTranslations("group")`, the group listed for the screen in
  `CLIENT_GROUPS`, and the screen wrapping them in
  `<NextIntlClientProvider messages={await getClientMessages(CLIENT_GROUPS.x)} timeZone="UTC">`.
- Words that depend on who is looking (a role, an owner-only title) are picked
  on the server and passed as props, never sent as a group.
- A screen inside `AuthShell` passes its banner as `sign={…}`.
- Relative times: `relativeTime(date, await relativeTimeVoice())`, on the
  server; a client component is handed the finished string.
- **English must not change by a byte.** Every suite reads English copy, and
  English is what CI's requests get. `verify:auth`'s section 15 is the
  pattern: the server-rendered strings word for word, `lang="en"`, the same
  text for every `Accept-Language` that names no other file, and a page source
  free of words from other screens — then, for each file in `messages/`, the
  same screen in that language, its words read from the file rather than
  written in the suite. Text only the client renders (an open menu) is not in
  the server's HTML; compare `npm run shots` before and after for that.

## Adding a language

A language is a file, and nothing else:

1. Add `messages/<code>.json`, named with the language's BCP 47 tag as `Intl`
   writes it — `de`, `pt-BR` — with as many keys as are translated so far. A
   key it does not have shows in English.
2. `npm run check:messages`. It picks the file up by itself, refuses a name
   that is not a language, and lists every key still to translate, as
   warnings. Its first line shows the name the picker will use:
   `de (Deutsch)`.
3. Add `docs/glossary/<code>.md` for whoever maintains it after you: the
   conventions (formal or informal address, typography, the platform's own
   word for a passkey) and the diner's words — the rail, the pass, the books,
   *order up* — with the reason for each choice. The 1950s-diner voice is where
   a word-for-word translation goes wrong, and the reasoning is what the next
   translator needs. [docs/glossary/fr.md](glossary/fr.md) is the example.

That is all. The picker on `/me` lists it, a browser asking for it gets it,
the settings page offers it as the instance default (and `DEFAULT_LOCALE` can
name it), mail to somebody who chose it is written in it, and `verify:auth`
and `verify:settings` check the picker, the browser, the choice and the
instance default for it on the next full run — no code names a language, the
tests included. It ships in the next image built: the
server finds the catalogues in its bundle, so a file copied into a running
container does nothing.
